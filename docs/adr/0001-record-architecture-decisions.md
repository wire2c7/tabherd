# 0001. 設計判断を ADR として記録する

- ステータス：Accepted
- 日付：2026-09-28

## コンテキスト

初期セットアップでは、フレームワーク、型チェックの設定、依存管理、ブランチ戦略など、多くの設計判断をした。その理由は会話やコミットメッセージに散らばっていて、後から「なぜこうなっているのか」をたどりにくい。

一方、`AGENTS.md` と `.claude/rules/` は「現在の規約」を書く場所で、変更の経緯や過去の議論は書かない方針になっている（`.claude/rules/docs.md`）。

## 検討した選択肢

- `AGENTS.md` に理由も書く：規約と経緯が混ざり、エージェントが毎回読む文書が長くなる。上記の方針とも衝突する
- コミットメッセージや PR 本文だけに残す：判断ごとにまとまっておらず、あとで探しにくい
- `docs/adr/` に ADR として残す：判断ごとに1ファイルにまとまり、置き換えの履歴もたどれる

## 決定

設計判断とその理由は、`docs/adr/` に ADR として記録する。`AGENTS.md`・`.claude/rules/` には「何をするか」だけを書き、「なぜ」の詳細は ADR を参照する。

## 結果

- 設計判断の背景を、判断単位でたどれるようになる
- 判断を変えるときは、新しい ADR を追加し、古い ADR のステータスを `Superseded by NNNN` にする手間がかかる

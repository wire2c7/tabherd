# 0025. タブイベントはルール変更のデバウンスの確定を待ってから判定する

- ステータス：Accepted
- 日付：2026-10-06
- 関連 Issue：#36

## コンテキスト

ルールの変更は 300ms デバウンス（`utils/grouping/debounce.ts`）してから反映し、反映時は「デバウンス開始前の oldRules」と「終了後の newRules」の2点だけを比べて（`utils/grouping/rule-change.ts` の `diffRules`）、既存のタブグループのタイトル・色の更新を計画する。

一方、タブの URL 変更等のイベント（`tabs.onUpdated`・`onAttached`）はデバウンスを待たず、そのときストレージにある最新のルールを即座に読んでタブを判定する（`entrypoints/background/grouping.ts` の `regroupTab`）。この2系統は同じ直列キュー（`utils/grouping/serial.ts`）に処理を積むため実行順序自体は直列になるが、`regroupTab` が「いつのルール値を読むか」は制御されておらず、デバウンス確定前の中間状態を読みうる。中間状態でタブグループが作られると、確定後の2点比較はその中間状態を経由したことを知らないため、作られたグループは古いタイトル・色のまま直らない。

再現の例は Issue #36 を参照。

## 検討した選択肢

- **A（採用）: タブイベントをデバウンスに合わせて待たせる**。`regroupTab` が、タブを判定する前に進行中のルール変更のデバウンスが確定するまで待つ。中間状態のルール値でグループが作られること自体が無くなるため根本原因を断てる。`plan.ts`・`rule-change.ts` は変更不要。影響は「ルール編集中（300ms以内）にタブを開く」という稀な重なりのときだけで、通常のタブ操作に遅延は生じない
- **B: 確定後に既存グループの色も原因を問わず直す**。`plan.ts` の判定を拡張し、タイトルが一致する既存グループでも色が食い違えば常に直す。原因を問わず収束する頑健さはあるが、将来「手動でタブグループの色を変える」運用と衝突しうる（タブイベントのたびに色を強制するようになる）上、どの経路で揃えるかの設計をさらに詰める必要があった
- **C: デバウンスの差分を2点比較でなく累積で追跡する**。理論上どんな経路で中間状態が作られても正しく扱えるが、`debounceChanges`・`diffRules` 双方の実装とテスト（property-based test を含む）が大きく複雑になる

待機の上限については、上限を設けないことにした。`waitUntilSettled()` は呼び出し時点で保留中のデバウンスが確定するまでだけ待ち、次に新しく始まるデバウンスは待たない。ルール編集は通常数秒以内に止まるため、実用上は数百ms程度で解決する想定で、上限を設ける実装の複雑さに見合わないと判断した。

## 決定

`utils/grouping/debounce.ts` の `debounceChanges` が `{ onChange, waitUntilSettled }` を返すようにし、`waitUntilSettled()` は保留中のデバウンスが無ければ即座に、あればリスナーの呼び出し（例外を含む）の後に解決する。`entrypoints/background/grouping.ts` の `regroupTab` は、タブを判定する前にこの `waitUntilSettled()` を待つ。待機に上限は設けない。

## 結果

- デバウンスの途中の中間状態のルールでタブグループが作られることが無くなり、ルールの名前・色の変更が既存のグループへ正しく反映される
- `plan.ts`・`rule-change.ts` の挙動は変わらないため、それらに対する既存のテスト・判定ロジックへの影響が無い
- `debounceChanges` の公開 API（戻り値の形）が関数から `{ onChange, waitUntilSettled }` に変わった
- 休みなく連続でルールを編集し続けると、その間タブの判定が遅れ続ける可能性があるが、実運用でそのような操作は想定しにくい
- `regroupTab` は確定後の `rules` を読めるようになったが、`titlesStore` は同じ直列キューで後ろに並ぶ `applyAndSaveTitles` の書き込みより先に読むため、名前が衝突するルールを編集した場合はまだ古い記録で判定してしまう残存の制約がある（#81）

# 0025. ルール変更の反映を、バーストの最初の変更時点でキューへ積む

- ステータス：Accepted
- 日付：2026-10-07
- 関連 Issue：#36、#81、#67

## コンテキスト

ルールの変更は 300ms デバウンス（`utils/grouping/debounce.ts`）してから反映し、反映時は「デバウンス開始前の oldRules」と「終了後の newRules」の2点だけを比べて（`utils/grouping/rule-change.ts` の `diffRules`）、既存のタブグループのタイトル・色の更新を計画する。

一方、タブの URL 変更等のイベント（`tabs.onUpdated`・`onAttached`）はデバウンスを待たず、そのときストレージにある最新のルールを即座に読んでタブを判定する（`entrypoints/background/grouping.ts` の `regroupTab`）。この2系統は同じ直列キュー（`utils/grouping/serial.ts`）に処理を積むため実行順序自体は直列になるが、`regroupTab` が「いつのルール値を読むか」は制御されておらず、デバウンス確定前の中間状態を読みうる。中間状態でタブグループが作られると、確定後の2点比較はその中間状態を経由したことを知らないため、作られたグループは古いタイトル・色のまま直らない（Issue #36）。

## 検討した選択肢

### 直し方

- **A: タブイベントがキューに積む前に、進行中のデバウンスの確定を待つ**。`regroupTab` 自体は待たない単純な形に戻し、呼び出し側（`tabs.onUpdated`・`onAttached`）が `waitUntilSettled()` を待ってから `enqueue` する。デッドロックしないが、「待ち行列なのに、並ぶこと自体を待たされる」という直感に反する
- **B: 確定後に既存グループの色も原因を問わず直す**。`plan.ts` の判定を拡張し、タイトルが一致する既存グループでも色が食い違えば常に直す。原因を問わず収束する頑健さはあるが、将来「手動でタブグループの色を変える」運用と衝突しうる
- **C: デバウンスの差分を2点比較でなく累積で追跡する**。理論上どんな経路で中間状態が作られても正しく扱えるが、`debounceChanges`・`diffRules` 双方の実装とテスト（property-based test を含む）が大きく複雑になる
- **D: タブイベントは到着順にキューへ積むが、順番が来て確定前なら自分をキューの末尾に積み直す**。Aと違い「並ぶこと自体は到着順」を保てるが、確定を確かめる仕組み（`waitUntilSettled()` のような Promise ではなく、即答できる判定）と、積み直しのたびに無限ループしない保証が別途必要で、Aより実装が複雑になる
- **E: キュー自体を、到着順ではなく優先度で並べ替えられる構造に作り変える**。確定した瞬間、すでに並んでいる依存タスクより前に割り込ませる。他の処理も使っている共有の `createSerialQueue` 自体の構造を変える必要があり、変更量・リスクが最も大きい
- **F（試作のみ、不採用）: regroupTab を待たせず、確定後の全体再判定（`regroupAllWindows`）で既存グループの色を無条件に直す**。実装して確かめたところ、**編集していない別のルールの、利用者が手動で変えた色まで巻き込んで強制的に戻してしまう**重大な副作用が見つかった。原因を絞り込んだ F2（「このルール変更で新しくタイトルを持ったルールだけ」に対象を絞る）でこの副作用は解消できたが、`RuleChange`（`diffRules` の戻り値）の拡張・関連する既存テストの更新など、変更範囲がA〜Eより広くなった
- **G（採用）: タブイベントは到着順にそのままキューへ積む。ルール変更の反映タスクだけ、バーストの最初の変更があった時点でキューへ積み、タスク自身がデバウンスの確定を待つ**。確定した際に反映タスクを積む処理（listener）は、キューへは積まない（最初の変更時点ですでに積んである）。これにより、タブイベントは常に到着順どおりに振る舞いながら（A・Dが崩した直感を壊さない）、同じバーストの範囲で見ると、反映タスクが常にタブイベントより先にキューへ入っている（先に積まれているため）ので、確定後の正しい rules・titles を使って判定できる。`plan.ts`・`rule-change.ts`・`regroup.ts` には一切手を入れず、Fで見つかった副作用も生じない（既存の、変更があったルールだけを直す `diffRules` の仕組みをそのまま使うため）

## 決定

`entrypoints/background/grouping.ts` の `regroupTab` は、ルール変更を待たない単純な形のままにする。`rulesReader.watch` のリスナー（`onRulesChanged`）が、ルール変更のバーストの最初の変更があった時点で、反映のタスク（`ruleChangeDebounce.waitUntilSettled()` を待ってから `applyAndSaveTitles` を呼ぶ）を `enqueue` する。同じバーストの2回目以降の変更では、タスクを積み直さない（`isBurstPending` で判定する）。

## 結果

- タブイベントは常に到着時点でそのままキューへ積まれる。「待ち行列に並ぶこと自体を待たされる」という直感に反する挙動が無い
- デバウンスの途中の中間状態のルールでタブグループが作られることが無くなり、ルールの名前・色の変更が既存のグループへ正しく反映される（Issue #36）
- 名前が衝突するルールを編集した直後にタブイベントが来ても、確定後の正しい `titlesStore` で判定し直されるため、誤った判定のまま残らない（Issue #81）
- `plan.ts`・`rule-change.ts`・`regroup.ts` の挙動は変わらないため、それらに対する既存のテスト・判定ロジックへの影響が無い。F・F2で検討した「既存グループの色を強制的に直す」仕組みも不要になった
- `debounceChanges`（`utils/grouping/debounce.ts`）の `waitUntilSettled()` は、このADRの検討・実装を通じて導入したもので、そのまま使う
- 休みなく連続でルールを編集し続けると、その間タブの判定が遅れ続ける可能性があるが、実運用でそのような操作は想定しにくい

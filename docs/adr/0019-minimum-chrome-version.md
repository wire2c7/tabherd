# 0019. 対応する最低の Chrome バージョンを 140 にする

- ステータス：Accepted
- 日付：2026-10-04
- 関連 Issue：#54

## コンテキスト

manifest に `minimum_chrome_version` が無く、拡張機能がどの Chrome から動くかを決めていなかった。コードは宣言の無いまま、次の版から使える API を前提にしていた（MDN の browser-compat-data で確認）。

- `tabGroups` API：Chrome 89
- `Array.prototype.toSorted`：Chrome 110
- `color-mix()`：Chrome 111
- `Promise.withResolvers`（#53 で追加）：Chrome 119

宣言より古い Chrome では、これらの API が無いため一部の操作が失敗する。#53 のレビューで見つかった。

前提と制約:

- 2026-10 の時点で、Chrome の安定版は 154、延長安定版は 152。延長安定版は 140（2025-09）、144（2026-01）、148（2026-05）と続く（Google の versionhistory API で確認）
- `minimum_chrome_version` より古い Chrome では、Chrome ウェブストアから拡張機能を入れられず、更新も届かない
- WXT は Vite の `build.target` を設定せず、Vite の既定（`baseline-widely-available`。`chrome111` 等）で構文を変換する。API は変換も補完もしない
- Oxlint には、API の対応版を検査するルールが無い

## 検討した選択肢

### 最低版

- **111**：Vite の既定の構文の変換先と `color-mix()` に合わせる。`Promise.withResolvers` を書き換える必要がある。約3年前の版で、古い版への配慮が新しい API を使う妨げになる
- **119**：今のコードのままで済む。約3年前の版で、111 と同じく古い版への配慮が続く
- **140**：2025-09 の延長安定版で、約1年前の版。更新の遅い端末や企業の管理端末も、年単位で古くなければ入る
- **148・152**：新しい API をより自由に使えるが、更新が半年・1か月遅れただけの端末に入らない

### 上げ方

- **必要になったら上げる**：最低版より新しい API を使いたいときに、その変更で上げる。定期的な作業は無い
- **定期的に上げる**：「約1年前の延長安定版」等の基準で見直す。古い版への配慮を続けずに済むが、見直す作業が増え、使う必要の無いときにも利用者を切り捨てる

### 最低版より新しい API の使用の防ぎ方

- **規約に書き、レビューで確かめる**：仕組みは増えない。見落としはレビューに頼る
- **Vite の `build.target` を最低版に合わせる**：構文は変換されるが、API は変換されず、今回の種類の問題は防げない
- **互換性を検査するツールを入れる**：Oxlint には該当するルールが無く、ESLint のプラグイン等を別に入れることになる

## 決定

- manifest の `minimum_chrome_version` を `"140"` にする（`wxt.config.ts`）
- 最低版は、140 より新しい API を使いたいときに、その変更で上げて ADR を書く。定期的には上げない
- 使う API は最低版で使えるものに限ることを規約（`AGENTS.md`）に書き、レビューで確かめる。`build.target` は Vite の既定のままにし、検査のツールは入れない

## 結果

- Chrome 140 以降なら、`tabGroups`・`toSorted`・`color-mix()`・`Promise.withResolvers` を含め、それまでに入った API を気にせず使える
- Chrome 140 より古い Chrome の利用者は、拡張機能を入れられず、更新も受け取れない
- 最低版より新しい API の使用は自動では検出されず、レビューで見落とすと、宣言した版で失敗する
- Vite の既定の構文の変換先（`chrome111`）は 140 より古いため、構文の点では問題にならない。Vite が既定を 140 より新しくしたら、`build.target` を合わせるかを改めて判断する

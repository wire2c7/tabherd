# 0016. タブの操作の計画を fast-check による Property Based Testing で確かめる

- ステータス：Accepted
- 日付：2026-10-02
- 関連 Issue：#46

## コンテキスト

タブのグループ化・並べ替えの計画は、純粋関数（`planGrouping`・`planGroupOrder`）で組み立てている。入力には、ピン留めのタブ・手動のグループ・同名のグループ・無効なルール等の組み合わせが多い。今のテストは例を挙げて確かめる形で、組み合わせを網羅できない。一方、成り立つべき性質（計画を適用した後の状態・冪等性）ははっきり書ける。

前提と制約:

- 単体テストは Vitest で書いている
- 依存パッケージは pnpm の `minimumReleaseAge`・`trustPolicy` で審査している（ADR 0006）
- 計画の関数はブラウザの API を呼ばない。計画を Chrome の API で実行した結果は E2E テストで確かめている（ADR 0013）

## 検討した選択肢

- **fast-check**：入力を生成し、失敗したら最小の反例に縮める（shrinking）。TypeScript で保守されている Property Based Testing のライブラリは事実上これだけ（jsverify・testcheck-js は更新が止まっている）
- **`@fast-check/vitest` を併せて使う**：`test.prop` 等で書き方が少し短くなるが、依存とその更新が増える
- **範囲を決めて小さな入力をすべて試す**：依存は増えず、結果が毎回同じ。ただし生成器を自前で書いて保守する手間は fast-check と変わらず、反例の縮小が無い
- **StrykerJS（ミューテーションテスト）**：今のテストの弱いところを測れるが、入力は増やさない
- **例のテストのままにする**：依存は増えないが、組み合わせの漏れを見つけられない

## 決定

- `planGrouping`・`planGroupOrder` の性質を、fast-check で生成した入力で確かめる。fast-check だけを devDependencies に加え、テストの中で `fc.assert` を呼ぶ。`@fast-check/vitest` は使わない
- 計画の結果は、テストの中に書いた単純なモデル（計画をスナップショットに適用する関数）で確かめる
- 例を挙げて確かめる既存のテストは、仕様の読みやすい例として残す
- StrykerJS は今回は入れない

## 結果

- 例のテストでは漏れていた入力の組み合わせで、計画の性質を確かめられる。失敗すると、縮めた反例と再現用の seed が出る
- seed を固定しないため、まれな反例が CI でだけ見つかることがある。見つかったら実装のバグとして直し、例のテストにも加える
- モデルが Chrome の実際の振る舞いとずれると、テストは通るのに本物では壊れうる。Chrome での振る舞いは E2E テストで確かめる
- 他の関数（`planGroupUpdates`・設定画面の関数等）へ広げるかは、効果を見てから決める

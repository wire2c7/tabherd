# Design

## Context

- ルールは `utils/rules/storage.ts` の `rulesItem`（`storage.defineItem<Rule[]>`）に保存し、background（`regroupAll`・タブのイベント・`rulesItem.watch`）と設定画面（`use-rules.ts` の読み込みと `watch`）が読む
- WXT の storage は、保存値が `null`・`undefined` なら fallback（空の一覧）を返すが、それ以外の値は形を確かめずに返す（`@wxt-dev/storage` の `getValueOrFallback`）
- 保存したログでは、配列でない値を壊れた値として扱う（`utils/logging/storage.ts` の `isStoredLogs`。#53）
- 警告以上のログは、その直前の処理のログとともに端末に保存され、保存は直近 500 件まで（`diagnostic-logging`）

## Goals / Non-Goals

**Goals:**

- 保存されたルールの形が壊れていても、background と設定画面が例外で止まらず、読める部分を使う
- 壊れていたことを、ログ（background）と画面（設定画面）で分かるようにする

**Non-Goals:**

- 壊れた値の自動の書き戻し（利用者が編集したときに保存される）
- 保存値の形を変える場合の移行（`rulesItem` の `version` と migrations で行う）

## Decisions

### 保存値を項目ごとに確かめ、読める部分を残す

`parseRules(value: unknown)` が、直したルールの一覧と、壊れていたかどうか（配列でなかったか、除いた・直したルールの件数）を返す。

- 保存値が配列でない → 空の一覧
- 要素がオブジェクトでない、`id`・`name` が文字列でない、`id` が上のルールと同じ → そのルールを除く。設定画面の編集・並び替えは `id` でルールを特定するため、同じ `id` は残せない。グループ名はグループと結び付くため、ほかの値で補わない
- `conditions` が配列でない → 条件なし（どの URL にも一致しない）
- 条件がオブジェクトでない、`type` が `contains`・`regex` 以外、`value` が文字列でない → その条件だけを除く
- `color` がタブグループの色でない → grey（`GROUP_COLORS` の先頭）
- 型に無いプロパティは捨てる。将来の版が加えた項目もありうるため、壊れていたことには数えない

採用理由: 1か所の破損で、ほかのルール・条件が使えなくなるのを避ける（Issue のヒアリングで決めた）。判定は手書きの関数にし、検証のライブラリは入れない。ルールの形は小さく、ログの `isStoredLogs` と同じく依存を増やさずに済む。

却下した案: 壊れたルールを丸ごと除く案は、条件1件の破損でルール全体が無効になる。1つでも壊れていればグループ化を止める案は、正しいルールまで止まる。

### 読み込みの入口を storage.ts にまとめる

`utils/rules/storage.ts` に、直した一覧を返す `readRules()` と、直した一覧で通知する `watchRules()` を置き、background と設定画面はこれを使う。`rulesItem` は保存（`setValue`）に使う。

### background は壊れた状態ごとに1回だけ警告する

`utils/rules/reader.ts` の `createRulesReader` が、`readRules`・`watchRules` を包んで警告を出す。`watch` では変更後の値だけを確かめる。background はタブのイベントのたびにルールを読むため、読むたびに警告すると、端末に保存するログ（500 件まで）が警告で埋まる。壊れた値を読んだら警告し、以後は壊れていない値を読むまで警告しない。警告には件数だけを書き、グループ名・条件は書かない（`diagnostic-logging` の「記録する情報の範囲」）。

### 設定画面は警告を出し、編集で保存し直す

設定画面は、読み込み・`watch` で受け取った値が壊れていれば一覧の上に警告を出す。利用者がルールを変更すると、直した一覧が保存され（今の `update` のとおり）、警告を消す。自動では書き戻さない（ヒアリングで決めた。壊れた値が編集まで残り、調べられる）。

## Risks / Trade-offs

- [利用者が編集するまで、壊れた部分の値はストレージに残り、background は読むたびに直す] → 直す処理はルールの件数に比例する小さい処理で、警告は状態ごとに1回だけにする
- [読み込みは非同期のため、壊れた値を保存する前に始まった読み込み（壊れていない値）が警告の後に届くと、壊れていない値を読んだとして、次に壊れた値を読んだときにもう一度警告する] → 警告が1回増えるだけで、ログが埋まることはない。インストール直後に壊れた値を保存する E2E テストで起きたため、テストは起動時の処理を待ってから壊れた値を保存する
- [除いたルールのグループのタブは、ルールの変更の反映で管理対象から外れうる] → 壊れたルールはもともと判定できない。利用者がルールを作り直せば戻る

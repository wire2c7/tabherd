# Design

## Context

- ルールは `utils/rules/storage.ts` の `rulesItem`（`storage.defineItem<Rule[]>`）に保存し、background（`regroupAll`・タブのイベント・`rulesItem.watch`）と設定画面（`use-rules.ts` の読み込みと `watch`）が読む
- WXT の storage は、保存値が `null`・`undefined` なら fallback（空の一覧）を返すが、それ以外の値は形を確かめずに返す（`@wxt-dev/storage` の `getValueOrFallback`）
- 保存したログでは、配列でない値を壊れた値として扱う（`utils/logging/storage.ts` の `isStoredLogs`。#53）
- 警告以上のログは、その直前の処理のログとともに端末に保存され、保存は直近 500 件まで（`diagnostic-logging`）

## Goals / Non-Goals

**Goals:**

- 保存されたルールの形が壊れていても、background と設定画面が例外で止まらず、読める部分を使う
- 壊れていたことを、ログ（background）と画面（設定画面）で分かるようにする

**Non-Goals:**

- 壊れた値の自動の書き戻し（利用者が編集したときに保存される）
- 保存値の形を変える場合の移行（`rulesItem` の `version` と migrations で行う）

## Decisions

### 保存値を項目ごとに確かめ、読める部分を残す

`parseRules(value: unknown)` が、直したルールの一覧と、壊れていたかどうか（配列でなかったか、除いた・直したルールの件数）を返す。

- 保存値が配列でない → 空の一覧
- 要素がオブジェクトでない、`id`・`name` が文字列でない、`id` が上のルールと同じ → そのルールを除く。設定画面の編集・並び替えは `id` でルールを特定するため、同じ `id` は残せない。グループ名はグループと結び付くため、ほかの値で補わない
- `conditions` が配列でない → 条件なし（どの URL にも一致しない）
- 条件がオブジェクトでない、`type` が `contains`・`regex` 以外、`value` が文字列でない → その条件だけを除く
- `color` がタブグループの色でない → grey（`GROUP_COLORS` の並びは新しいルールの色を選ぶ順番のため、それに頼らず直接書く）
- 型に無いプロパティは捨てる。将来の版が加えた項目もありうるため、壊れていたことには数えない

採用理由: 1か所の破損で、ほかのルール・条件が使えなくなるのを避ける（Issue のヒアリングで決めた）。

判定は valibot のスキーマで行い、`Rule`・`Condition`・`GroupColor` の型はスキーマから作る（`utils/rules/types.ts`。ADR 0020）。まず `RuleSchema` で確かめ、通らなければ `id`・`name` だけを確かめるスキーマで読み、色と条件を直す。条件は1件ずつ `ConditionSchema` で確かめる。valibot の `object` は型に無いプロパティを捨てる。

却下した案: 壊れたルールを丸ごと除く案は、条件1件の破損でルール全体が無効になる。1つでも壊れていればグループ化を止める案は、正しいルールまで止まる。

### 読み書きの入口を storage.ts にまとめる

`utils/rules/storage.ts` は `rulesItem` を外へ出さず、直した一覧を返す `readRules()`、直した一覧で通知する `watchRules()`（変更後の一覧だけ）・`watchRuleChanges()`（変更前の一覧も）、保存する `writeRules()` を出す。`rulesItem` の型は `Rule[]` だが、読んだ値は壊れていることがあり、そのまま使うと #56 と同じ例外になるため、直さずに読む経路を残さない。設定画面は入力のたびに保存するため、変更前の一覧を使わない設定画面は `watchRules()` で購読し、変更前の一覧を直す手間を省く。

### background は壊れた状態ごとに1回だけ警告する

`utils/rules/reader.ts` の `createRulesReader` が、`readRules`・`watchRuleChanges` を包んで警告を出す。`watch` では変更後の値だけを確かめる。background はタブのイベントのたびにルールを読むため、読むたびに警告すると、端末に保存するログ（500 件まで）が警告で埋まる。壊れた値を読んだら警告し、以後は壊れていない値を読むまで警告しない。警告には件数だけを書き、グループ名・条件は書かない（`diagnostic-logging` の「記録する情報の範囲」）。

警告したかどうかは `storage.session`（`session:rulesDamageWarned`）に置く。Service Worker は30秒操作が無いと止まり、変数が消えるため、変数だけに置くと起き直すたびに警告する。`storage.session` はブラウザを閉じるまで残る。Service Worker が起動してから最初の判定で一度だけ読み、以後は変数に写した値で判定し、変わったときだけ書く。判定と変数の書き換えは `await` を挟まずに行い、同時に読んだ判定が二重に警告しないようにする。

却下した案: `storage.local` に置く案は、ブラウザを起動し直しても警告しないため、起動のたびに1回は残したい（いつから壊れているかがログで分かる）警告まで止まる。警告を一定の時間ごとにだけ出す案は、Spec の「壊れていない値を読むまで繰り返さない」と合わない。

### 設定画面は警告を出し、編集で保存し直す

設定画面は、読み込み・`watch` で受け取った値が壊れていれば一覧の上に警告を出す。利用者がルールを変更すると、直した一覧が保存され（今の `update` のとおり）、保存し終えたら警告を消す。保存に失敗したときはストレージに壊れた値が残っているため、警告を消さない。自動では書き戻さない（ヒアリングで決めた。壊れた値が編集まで残り、調べられる）。

## Risks / Trade-offs

- [利用者が編集するまで、壊れた部分の値はストレージに残り、background は読むたびに直す] → 直す処理はルールの件数に比例する小さい処理で、警告は状態ごとに1回だけにする
- [valibot の分だけ拡張機能が大きくなる] → `background.js`・設定画面のチャンクとも minify 後に約 4 kB 増える（ADR 0020）
- [読み込みは非同期のため、壊れた値を保存する前に始まった読み込み（壊れていない値）が警告の後に届くと、壊れていない値を読んだとして、次に壊れた値を読んだときにもう一度警告する] → 警告が1回増えるだけで、ログが埋まることはない。インストール直後に壊れた値を保存する E2E テストで起きたため、テストは起動時の処理を待ってから壊れた値を保存する
- [除いたルールのグループのタブは、ルールの変更の反映で管理対象から外れうる] → 壊れたルールはもともと判定できない。利用者がルールを作り直せば戻る

# Design

## Context

- Chrome の安定版は 154（2026-09-22）、延長安定版は 152。延長安定版は 140（2025-09-08）、144（2026-01-20）、148（2026-05-11）と続く（Google の versionhistory API で確認）
- コードが前提にしている版は、`tabGroups` が 89、`toSorted` が 110、`color-mix()` が 111、`Promise.withResolvers`（#53）が 119（MDN の browser-compat-data で確認）
- WXT は Vite の `build.target` を設定せず、Vite の既定（`baseline-widely-available`。`chrome111` 等）で構文を変換する。API は変換も補完もしない
- 宣言より新しい API の使用を検出する仕組みは無い。Oxlint には、API の対応版を検査するルールが無い

## Goals / Non-Goals

**Goals:**

- 拡張機能が動く最低の Chrome バージョンを manifest で宣言し、それより古い Chrome に入らないようにする

**Non-Goals:**

- 宣言より新しい API の使用を自動で検出すること（規約とレビューで防ぐ）
- Vite の `build.target` を最低版に合わせること

## Decisions

### 最低版を 140 にする

`minimum_chrome_version` を `"140"`（2025-09 の延長安定版）にする。

- 採用理由: 約1年前の版で、更新の遅い端末や企業の管理端末も、年単位で古くなければ入る。それまでに入った API は気にせず使える
- 却下した案: 111・119（今のコードが前提にしている版）は約3年前で、古い版への配慮が新しい API を使う妨げになる。148・152 は、更新が半年・1か月遅れただけの端末に入らない

### 必要になったら上げる

最低版は、140 より新しい API を使いたいときに、その変更で上げて ADR を書く。定期的には上げない。

- 却下した案: 「約1年前の延長安定版」等の基準で定期的に上げる。古い版への配慮を続けずに済むが、見直す作業が増え、使う必要の無いときにも利用者を切り捨てる

### `build.target` は変えない

Vite の既定の `chrome111` は 140 より古く、変換した構文は 140 でそのまま動く。最低版に合わせても、構文の変換が少し減るだけで、API の問題は防げない。

## Risks / Trade-offs

- [宣言より新しい API を使い、宣言した版で失敗する] → `AGENTS.md` の規約で、使う API を最低版で使えるものに限り、レビューで確かめる
- [Chrome 140 より古い Chrome の利用者が、入れられなくなる・更新が届かなくなる] → 約1年前の版を選び、影響を小さくする

# Design

## Context

- `entrypoints/background.ts` は仮の処理のみ、`entrypoints/options/` は見出しだけで、機能のコードはまだない
- manifest の権限は `storage`・`tabGroups`・`tabs` がすでにある（`wxt.config.ts`）
- MV3 の background は Service Worker で、しばらく操作がないと停止する。メモリ上の状態は再起動で失われる
- タブグループの ID はブラウザの再起動で変わる。同じウィンドウ・同じタイトルのグループを複数作れる
- テストは Vitest（`WxtVitest` プラグイン）。WXT の fake-browser は `tabGroups` に対応していないため、ブラウザの API を呼ぶ部分は単体テストしにくい
- `tsconfig.app.json` の `include` は `entrypoints` だけで、新しいディレクトリを置くなら追加が必要

## Goals / Non-Goals

**Goals:**

- ルールの判定とグループ操作の計画を、ブラウザの API から切り離した純粋関数にし、Vitest で検証できるようにする
- Service Worker が停止・再起動しても、状態を持ち越さずに正しく動く
- イベントが立て続けに来ても、重複したグループを作らない

**Non-Goals:**

- ルールの `storage.sync` での端末間同期、インポート・エクスポート
- シークレットウィンドウへの対応（拡張機能はデフォルトで許可されていない）
- タブ単位の除外や、ドメイン一致・前方一致など部分一致・正規表現以外の条件
- ユーザーが手でグループを動かしたときに、その場で並びを戻すこと（次の判定のときに戻る）

## Decisions

### モジュール構成

WXT の規約のディレクトリに置く。

- `utils/rules/`: ルールの型・保存（ストレージのアイテムの定義）・URL の判定・有効性の検証
- `utils/grouping/`: ウィンドウのスナップショットとルールから、グループ操作の計画を組み立てる純粋関数。計画をブラウザの API で実行する処理は別ファイルに分ける
- `components/rule-settings/`: 設定画面の Preact コンポーネント。`entrypoints/popup/` と `entrypoints/options/` の両方から描画する
- `entrypoints/background.ts`: イベントの購読と、処理の直列化だけを受け持つ

WXT の auto-import には頼らず、明示的に import する（既存の `entrypoints/options/main.tsx` と同じ）。`tsconfig.app.json` の `include` に `utils`・`components` を加える。

### ルールのデータ

```ts
type GroupColor = "grey" | "blue" | "red" | "yellow" | "green" | "pink" | "purple" | "cyan" | "orange";
type Condition = { type: "contains" | "regex"; value: string };
type Rule = { id: string; name: string; color: GroupColor; conditions: Condition[] };
```

- `id` は `crypto.randomUUID()` で作る。ルールの名前変更・削除の検出と、UI の `key` に使う
- 保存は WXT の `storage.defineItem<Rule[]>("local:rules", { fallback: [], version: 1 })`。後でデータの形を変えるときは WXT の `migrations` で移行する
- `storage.sync` は1アイテム 8KB の上限があり、正規表現の多いルールで超えうるため使わない。同期は Non-Goals
- 新しいルールの色は、既存のルールで使われていない色を `GroupColor` の順に選ぶ。grey は目立たないため候補から外し、ほかの色がすべて使われているときだけ使う

### 管理対象のグループはタイトルで識別する

ウィンドウ内で、タイトルが有効なルールのグループ名と一致するタブグループを、そのルールのグループとみなす。

- 採用理由: 状態を保存しないため、Service Worker の再起動やブラウザの再起動（グループ ID が変わる）でも食い違わない
- 却下した案: ルールの ID とグループの ID の対応を `storage.session` に保存する。再起動のたびに対応を作り直す処理が要り、ユーザーがグループを閉じた・作り直したときに対応がずれる
- 影響: ユーザーが手でルールと同じ名前のグループを作ると、管理対象になる。ルールと同じ名前で意図的に作ったものとみなし、許容する
- 同じタイトルのグループが1つのウィンドウに複数あるときは、タブバーで左にあるものを使う

### 計画と実行を分ける

グループ操作は次の2段階にする。

1. 計画: ウィンドウのスナップショット（タブの ID・URL・ピン留め・所属グループ、グループの ID・タイトル・色）、ルールの一覧、判定するタブの集合、旧いルールの名前を受け取り、操作の一覧を返す純粋関数（`utils/grouping/plan.ts`・`rule-change.ts`）
2. 実行: 操作を順にブラウザの API（`tabs.group`・`tabs.ungroup`・`tabGroups.update`・`tabGroups.move`）で行う（`utils/grouping/execute.ts`）

操作の種類は「既存のグループへ入れる」「新しいグループを作って入れる（`tabs.group` の後に `tabGroups.update` でタイトル・色を付ける）」「グループから外す」「グループのタイトル・色を変える」「グループを移動する」。

- 採用理由: fake-browser が `tabGroups` に対応していなくても、仕様のシナリオのほとんどを計画のテストで確かめられる
- スナップショットのタブはタブバーの左から順に並べる。同名のグループのうち左のものは、タブの並びで最初に現れるグループとして求める（`tabGroups.query` の結果の順はタブバーの順と限らないため）
- 計画では、同じグループへ入れるタブ・同じルールのグループを作るタブを1つの操作にまとめる
- 実行中に1つの操作が失敗したとき（スナップショットの後にタブが閉じられた等）は、ログに出して残りの操作を続ける
- 並び（#16）は、グループ化の実行後にスナップショットを取り直して計画する。グループの大きさが変わった後の位置で計算するため

### 判定するタブの範囲

- `tabs.onUpdated`（`changeInfo.url` があるとき）・`tabs.onAttached`: そのタブだけを判定する。手で管理対象のグループへ入れた・外したタブを、関係ないイベントで勝手に戻さないため
- `runtime.onInstalled`・`runtime.onStartup`・ルールの変更: すべてのウィンドウのすべてのタブを判定する
- どちらの場合も、判定の後にそのウィンドウのグループの並びを揃える
- 対象は通常のウィンドウ（`windowType: "normal"`）だけにする。ポップアップ等のウィンドウにはタブグループを作れないため
- ウィンドウごとの計画・実行は並行して行う。グループはウィンドウごとに作るため、ウィンドウをまたいで操作が干渉しない

`tabs.onCreated` は購読しない。新しいタブは URL が決まった時点で `tabs.onUpdated` が来るため。

### ルールの変更の差分

ルールの変更は WXT の `watch` で新旧の一覧を受け取り、`id` で突き合わせる。

- 比べるのは変更前・変更後のどちらでも有効なルールだけにする（無効なルールのグループは管理対象でないため）
- 名前・色が変わったルール: 旧い名前のグループ（複数あればすべて）のタイトル・色を新しい値に変える（全体の判定の前に行う）。名前を入れ替えた場合も、変更前のスナップショットのグループ ID に対して操作するため食い違わない
- 旧い名前（変更前は有効で、変更後は有効なルールの名前でなくなった名前）: 削除のほか、名前を空にして無効になったルールと、名前を変えたルールの旧い名前が当たる。変更後は管理対象でなくなるため、全体の判定の計画にこの名前も渡して管理対象として扱い、そのグループのタブを一致しなければ外す

設定画面では入力のたびに保存するため、background はルールの変更を 300ms デバウンスしてから反映する。グループ名の入力途中の名前で、グループを作り直し続けないため。

### 処理の直列化

イベントごとの処理を1本の Promise のチェーンにつなぎ、前の処理が終わってから次の処理を始める。各処理は開始時にスナップショットを取り直す。

- 理由: `tabs.group` でグループを作ってからタイトルを付けるまでのあいだに、同じルールに一致する別のタブのイベントを処理すると、同名のグループが2つできるため
- 処理中の例外はログに出してチェーンを続ける（1回の失敗で以降の処理を止めない）
- ルールも各処理の開始時にストレージから読み直す。ルールの変更の処理だけは、デバウンスでまとめた変更の最初の変更前の一覧と最後の変更後の一覧を使う

### タブの編集ができないときのリトライ

ユーザーがタブをドラッグしているあいだは、タブ・グループの操作が `Tabs cannot be edited right now` のエラーで失敗する。このエラーのときだけ、100ms から倍々に（100・200・400・800・1600ms）待って、5回までやり直す。API の呼び出し1回ごとにやり直すため、グループを作ってからタイトル・色を付けるまでの途中で失敗しても、作ったグループをやり直しで重ねて作らない。

### 設定画面

- ポップアップとオプションページで同じコンポーネントを描画する。ポップアップは Chrome の上限（幅 800px・高さ 600px）に収まるよう幅を固定し、一覧は縦にスクロールする
- ストレージの `watch` で変更を受け取り、ポップアップとオプションページを同時に開いていても表示を揃える
- 変更は入力のたびに保存する。ポップアップはフォーカスが外れると即座に閉じるため、保存を遅らせると入力が失われる
- 正規表現の検証は `utils/rules/` の関数を background と共用する

### ドラッグでの並び替え

ライブラリを使わず、HTML5 Drag and Drop（`draggable` と `dragstart`・`dragover`・`drop`）で作る。キーボード用に各ルールに「上へ」「下へ」のボタンを置く。

- 採用理由: 縦1列の並び替えだけで足り、依存を増やさない（ADR 0006 のサプライチェーンの方針とも合う）
- 却下した案: dnd-kit は React 向けで `preact/compat` の設定が要る。SortableJS は DOM を直接並べ替えるため、Preact の仮想 DOM と食い違う
- 判断は #18 で ADR に残す

## Risks / Trade-offs

- [ユーザーがルールと同じ名前のグループを手で作ると管理対象になる] → 仕様として許容し、設定画面の説明に書く
- [計画のテストでは、ブラウザの API の実際の振る舞い（`tabs.group` 後のタブの位置等）を確かめられない] → 実行部分は薄く保ち、`pnpm dev` で起動したブラウザで各シナリオを手で確かめる
- [タブが多いウィンドウで全体の判定をすると API の呼び出しが多い] → 計画で変更のないタブ・グループには操作を出さず、並びも正しければ移動しない
- [管理対象のグループへ手で入れた一致しないタブは、ルールの変更時の全体の判定で外れる] → 仕様どおりとし、手でまとめたいタブは別名のグループに入れる運用とする
- [グループ名の入力途中の変更が 300ms を超えて止まると、途中の名前でグループの名前が変わる] → 名前の変更はタイトルの変更で済み、タブは動かないため許容する

## Migration Plan

初めての機能で、移行するデータはない。ストレージのデータの形を変えるときは、`storage.defineItem` の `version` を上げて `migrations` を書く。

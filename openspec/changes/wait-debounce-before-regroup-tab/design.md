# Design

## Context

`entrypoints/background/grouping.ts` の `regroupOnEvents` は、ルールの変更（`rulesReader.watch`）を `debounceChanges`（300ms）でまとめ、確定後に `applyAndSaveTitles` → `diffRules` で「デバウンス開始前の oldRules」と「終了後の newRules」の2点だけを比べて、既存のタブグループのタイトル・色の更新を計画する。

一方、`tabs.onUpdated`・`onAttached` はデバウンスを待たず、そのときストレージにある最新のルールを `readRulesState()` で読んで `regroupTab` が即座にタブを判定する。この2系統が同じ `createSerialQueue`（`utils/grouping/serial.ts`）に処理を積むため実行順序は直列になるが、`regroupTab` が「いつのルール値を読むか」は制御されておらず、デバウンス確定前の中間状態を読みうる。中間状態でタブグループが作られると、確定後の2点比較はその中間状態を経由したことを知らないため、作られたグループは古いタイトル・色のまま直らない（Issue #36）。

この不具合を「タブイベントがデバウンスの確定を待つ」方向で直そうとすると、`regroupTab` が参照する `titlesStore` 自体の更新（`applyAndSaveTitles` が書く）はキューの後ろに並ぶため、名前が衝突するルールを編集した直後は古い `titlesStore` のまま判定してしまう（Issue #81）。

## Goals / Non-Goals

**Goals:**

- デバウンスの途中の中間状態のルール値で、タブイベントがタブグループを作ってしまうこと自体を無くす（Issue #36）
- タブイベントが、進行中のルール変更の編集内容（`titlesStore` を含む）を正しく反映した状態で判定されるようにする（Issue #81）
- タブイベントの判定自体には、通常時（ルールを編集していないとき）の遅延を一切持ち込まない
- `plan.ts`・`rule-change.ts`・`regroup.ts` の既存の挙動（差分計算・判定ロジック）には手を入れない

**Non-Goals:**

- デバウンスの差分の取り方自体の変更（中間状態の累積追跡）は行わない
- `createSerialQueue`（直列キュー）自体の構造（到着順の FIFO）は変更しない

## Decisions

### 直し方

**選んだ方針（案G）**: タブイベントは、これまで通り発生した時点でそのまま直列キューへ積む（待たせない）。ルールの変更（`rulesReader.watch`）のバーストの**最初の**変更があった時点で、反映のタスク（`ruleChangeDebounce.waitUntilSettled()` を待ってから `applyAndSaveTitles` を呼ぶ）を直列キューへ積む。同じバーストの2回目以降の変更では、タスクを積み直さない。

この結果、ルール変更の反映タスクは、同じバーストと重なるどのタブイベントよりも**先に**キューへ入っている（タブイベントが発生する前、バーストの最初の変更の時点ですでに積んであるため）。タブイベント自身は何も待たないが、キューのFIFO順により、反映タスクの実行（デバウンスの確定を待ってから行う）が終わるまで自分の番が回ってこない。反映タスクが完了した時点で `titlesStore` を含む全ての状態が確定後の正しい値になっているため、その後に実行されるタブイベントの判定も正しくなる。

**検討した選択肢**:

- **A: タブイベントをキューに積む前に、進行中のデバウンスの確定を待たせる**。`regroupTab` の呼び出し側が `waitUntilSettled()` を待ってから `enqueue` する。デッドロックしないが、「待ち行列なのに、並ぶこと自体を待たされる」という直感に反する
- **B: 確定後に既存グループの色も原因を問わず直す**。`plan.ts` の判定を拡張し、タイトルが一致する既存グループでも色が食い違えば常に直す。原因を問わず収束する頑健さはあるが、将来「手動でタブグループの色を変える」運用と衝突しうる
- **C: デバウンスの差分を2点比較でなく累積で追跡する**。理論上どんな経路で中間状態が作られても正しく扱えるが、実装とテスト（property-based test を含む）が大きく複雑になる
- **D: タブイベントは到着順にキューへ積むが、自分の番が来て確定前なら自分をキューの末尾に積み直す**。Aと違い「並ぶこと自体は到着順」を保てるが、確定を即答で確かめる仕組みと、積み直しが無限ループしない保証が別途必要で、Aより実装が複雑になる
- **E: キュー自体を、到着順ではなく優先度で並べ替えられる構造に作り変える**。他の処理も使っている共有の `createSerialQueue` 自体の構造を変える必要があり、変更量・リスクが最も大きい
- **F（試作して不採用）: `regroupTab` を待たせず、確定後の全体再判定（`regroupAllWindows`）で既存グループの色を無条件に直す**。実装して確かめたところ、編集していない別のルールの、利用者が手動で変えた色まで巻き込んで強制的に戻してしまう重大な副作用が見つかった。対象を「このルール変更で新しくタイトルを持ったルールだけ」に絞った F2 で副作用は解消できたが、`RuleChange`（`diffRules` の戻り値）の拡張・既存テストの更新など、変更範囲がA〜Eより広くなった

G は、タブイベントの「到着順にそのまま積む」という直感（Aで崩れた点）を保ちながら、Fで見つかった副作用（既存の `diffRules` の仕組みを変えずに済むため）も生じない。

### 待機の上限

**決定**: 上限を設けない。`waitUntilSettled()` は、呼び出し時点で保留中のデバウンスが確定するまでだけ待つ（次に新しく始まるデバウンスは待たない）。ルール編集は通常数秒以内に止まるため、実用上は数百ms程度で解決する想定。

## Risks / Trade-offs

- [リスク] 休みなく連続でルールを編集し続けると、その間のタブイベントの判定がすべて確定を待つ反映タスクの後ろに並び続ける → [軽減] `waitUntilSettled()` は呼び出し時点で保留中の1回分だけを待つため、次の編集が増えても待ち時間は際限なく伸びない。実運用でそのような操作は想定しにくい
- [リスク] `debounceChanges` の公開 API（戻り値の形）が変わる → [軽減] 利用箇所は `entrypoints/background/grouping.ts` の1箇所のみで、同じ変更の中で追従する
- [リスク] デバウンスの確定処理（リスナーの呼び出し）が例外を投げると、待機中の `waitUntilSettled()` が解決しなくなる → [軽減] `try/finally` で、例外が起きても待機中の呼び出し元を必ず解決する
- [リスク] バーストの最初の変更時点で反映タスクをキューへ積むため、キューに積んだ後にバーストが始まったのか・続いているのかを `isBurstPending` のようなフラグで追跡する必要がある → [軽減] フラグはクロージャ内のローカル変数で、`regroupOnEvents` の呼び出し（Service Worker の起動）ごとに1つだけ。単体テストで、1バースト・連続した2回の変更・バーストなしの3パターンを確認済み

# Design

## Context

- `planGrouping` はタブごとに判定（keep・ungroup・group）を出し、group のタブは、同じタイトルのグループのうちタブバーで左のもの（`findLeftmostGroupIds`）へ入れる。無ければ新しく作る
- 操作は「外す → 既存のグループへ入れる → 新しく作る」の順に出し、`executeOperations` が順に実行する。失敗した操作はログに出して次へ進む
- Chrome は、タブが無くなったグループを消す。外す操作でも、別のグループへ移す操作（`tabs.group`）でも同じ（#47 で確かめた）

## Goals / Non-Goals

**Goals:**

- 計画のどの操作を先に実行しても、既存のグループへ入れる操作の入れる先が消えていない

**Non-Goals:**

- スナップショットを取った後にユーザーがタブを閉じる・動かす等で、入れる先が消える場合（今と同じく、ログに出して次の判定で直る）
- 操作の順の変更

## Decisions

### 元のタブが残るグループだけを入れる先にする

判定を先にすべてのタブについて出し、判定が keep のタブと判定の対象外のタブ（`targetTabIds` に無いタブ）が1つ以上残るグループを「残るグループ」とする。入れる先は、残るグループのうちタブバーで左のものにする。残る同名のグループが無ければ、新しく作る。

- 採用理由: 残るグループには計画の後もタブがあるため、どの順に実行しても消えない。2つのグループの中身が入れ替わる場合も、どちらも残らないため新しく作り、正しく分かれる。変更は `plan.ts` の中で閉じ、操作の型と `executeOperations` は変わらない
- 却下した案: 操作の順を「入れる・作る → 外す」に変える案は、別のグループへ移す操作でグループが空になる場合（#47 の追記）を直せない。実行の時点で、入れる先が無ければ作る案（`add-to-group` にタイトル・色を持たせる）は、計画の型と実行の両方が変わり、純粋関数のテストで確かめられなくなる
- 消えるグループには、元のタブを外す・移す操作だけが出る。新しく作るグループのタイトル・色はルールのものになるため、消えるグループの色（ユーザーが変えたもの等）は引き継がない

## Risks / Trade-offs

- [左のグループが消えて右の同名のグループへ入るため、「左のグループへ入れる」の見た目と違う結果になる] → 左のグループは計画の後に無くなるため、残るグループのうち左のものへ入れるのが同じ規則の自然な延長になる。Spec の「タブの判定とグループ化」に明記する
- [消えるグループの位置にあったタブは、新しく作るグループへ入り、位置が変わる] → 並びは続く `planGroupOrder` がルールの順に揃える

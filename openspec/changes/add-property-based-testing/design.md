# Design

## Context

- 計画の関数は純粋関数で、ブラウザの API を呼ばない。入力は `WindowSnapshot`（タブは左から順、グループの情報）とルールの一覧で、出力は `GroupOperation` の配列。計画は `executeOperations` が順に Chrome の API で実行する
- `planGrouping` は、ピン留めされたタブ・管理対象でないグループ（タイトルが有効なルールの名前でも `retiredNames` でもない）のタブ・スナップショットに無いグループのタブには操作を出さない。同名のグループが複数あるときは、左のグループへ入れる
- `planGroupOrder` は、管理対象のグループをピン留めのタブの直後からルールの順に並べる `move-group` を出す。並びを追いながら、移動は常に今より左（または同じ位置）になる
- Chrome では、ピン留めされたタブは常に左端にあり、グループには入らない。グループのタブは連続して並ぶ
- 単体テストは Vitest（`*.test.ts`）。`tsconfig.node.json`・`.oxlintrc.jsonc` はテストを `*.test.ts` で見分ける

## Goals / Non-Goals

**Goals:**

- `planGrouping`・`planGroupOrder` の性質を、生成した多様な入力で確かめる
- 失敗したとき、fast-check が縮めた反例と再現用の seed がテストの出力に出る

**Non-Goals:**

- `planGroupUpdates`・`diffRules`・`components/rule-settings/` の関数の性質（効果を見てから別の Issue で広げる）
- `planGrouping` の後に `planGroupOrder` を続けて実行する `groupAndArrange` の組み合わせ（ブラウザの API を呼ぶため）
- Chrome の API の振る舞いそのものの検証（E2E テストの担当）

## Decisions

### fast-check をそのまま使う

`fast-check` だけを devDependencies に加え、テストの中で `fc.assert(fc.property(...))` を呼ぶ。

- 採用理由: TypeScript で保守されている Property Based Testing のライブラリは、事実上 fast-check だけ。入力の生成と、失敗したときの反例の縮小（shrinking）が揃う
- `@fast-check/vitest`（`test.prop` 等）は使わない。書き方が少し短くなるだけで、依存とその更新（Renovate・ADR 0006 の審査）が増えるため
- 却下した案: 範囲を決めて小さな入力をすべて試す方法は、依存は増えないが、生成器を自前で書いて保守する手間は fast-check と変わらず、反例の縮小が無い。StrykerJS（ミューテーションテスト）はテストの質を測るもので入力を増やさないため、今回は入れない
- 実行の回数は既定（100 回）、seed は固定しない。CI で失敗したら、出力の seed と path で再現する

### 性質のテストは1つのファイルにまとめる

`utils/grouping/properties.test.ts` に、arbitrary・モデル・両方の関数の性質を置く。

- 採用理由: arbitrary とモデルは両方の関数で共有する。補助を別のファイル（`*.test.ts` 以外）に分けると、`tsconfig.node.json`・`tsconfig.app.json`・`.oxlintrc.jsonc` でテスト用のファイルとして扱う設定を足す必要がある
- 例を挙げて確かめる既存のテスト（`plan.test.ts`・`order.test.ts`）は残す。仕様の読みやすい例として役に立つため

### arbitrary

Chrome が作りうるウィンドウだけを生成する。

- タブの並びは、ピン留めされたタブ（グループに入らない）を先頭に、グループに入っていないタブとグループ（1つ以上の連続したタブ）を並べる形で作る。こうするとグループのタブは必ず連続する
- グループのタイトルとルールの名前は、少数の候補（空文字列を含む）から選ぶ。同名のグループ・管理対象でないグループ・無効なルール（空の名前・名前の重複）が頻繁に現れるようにするため
- タブの URL とルールの条件も少数の部品から組み立て、条件に一致するタブと一致しないタブが両方現れるようにする。条件には `contains` と `regex`（構文が不正なものを含む）を使う
- まれに、スナップショットのグループの一覧に無いグループのタブを混ぜる（スナップショットの取得の途中でグループが変わった場合）
- `planGrouping` の `targetTabIds`（省略を含む）と `retiredNames` も生成する

### 計画を適用するモデル

テストの中に、計画の操作をスナップショットに適用する関数を書く。

- `ungroup`・`add-to-group`・`create-group` はタブの所属だけを変える（`create-group` は新しい ID のグループを加える）。Chrome はこれらの操作でタブの位置も変えるが、`planGrouping` の判定は所属とタイトルで決まり、位置は同名のグループのどれを選ぶかにしか使わないため、所属だけで性質を確かめられる。タブがなくなったグループは一覧から除く
- `move-group` は、グループのタブを取り出し、先頭が `index` に来るように差し込む。今より左（または同じ位置）への移動だけを受け付け、右への移動は例外にする。右への移動は Chrome の `index` の解釈が取り出した後か前かで変わるうえ、`planGroupOrder` は左にしか動かさない設計のため

### 確かめる性質

`planGrouping`:

- 計画を適用すると、判定の対象のタブのうち、ピン留めでなく、管理対象のグループに入っているかグループに入っていないタブは、`findMatchingRule` が返すルールの名前のグループに入っている（一致するルールが無ければグループに入っていない）
- ピン留めされたタブ・管理対象でないグループのタブ・スナップショットに無いグループのタブ・判定の対象外のタブは、所属が変わらない
- すでに正しいグループに入っているタブには操作を出さない。各タブは高々1つの操作にしか現れない
- 計画を適用した後に同じ条件でもう一度計画すると、操作は空になる（冪等）

`planGroupOrder`:

- 計画を適用すると、ピン留めのタブの直後に管理対象のグループがルールの順に並び、同じルールのグループは元の左右の順のまま続く。その後ろに、管理対象でないタブ・グループが元の相対的な順のまま並ぶ
- 移動はすべて今より左（または同じ位置）で、`index` はピン留めのタブの数以上
- タブの集合と各タブの所属は変わらない
- 計画を適用した後にもう一度計画すると、操作は空になる（冪等）

## Risks / Trade-offs

- [モデルが Chrome の実際の振る舞いとずれると、テストは通るのに本物では壊れる] → モデルは位置を変える操作を `move-group` の左への移動に限って単純に保つ。Chrome での並びは既存の E2E テスト（`e2e/group-order.e2e.ts`）が確かめる
- [期待する所属を `findMatchingRule` で求めるため、一致の判定そのもののバグは見つけられない] → 一致の判定は `match.test.ts` が例で確かめる。性質のテストの対象は、判定の結果を操作に組み立てる部分
- [seed を固定しないため、まれな反例が CI でだけ見つかる] → 見つかった反例は実装のバグとして直し、例のテストにも加える
- [性質のテストが実装と同じ考え方で書かれ、同じ誤りを含む] → 実装をわざと壊して、性質のテストが失敗することを確かめる
